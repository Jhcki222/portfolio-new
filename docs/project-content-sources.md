## 기술 판단과 보강

- **CDC:** 이벤트를 중복 전달할 수 있다는 전제로 영속 등록 후 offset 커밋, 현재 원천 재조회와 조건부 게시를 설명했다. Kafka–MongoDB 전체 exactly-once나 commit 직후 무지연 보장은 추가하지 않았다. 참고: [Debezium MySQL 문서](https://debezium.io/documentation/reference/stable/connectors/mysql.html).
- **WebFlux:** JVM 전체 스레드와 Tomcat 요청 스레드, monitor-blocked와 외부 I/O 대기를 구분했다. 이벤트 루프의 블로킹 호출 방지와 동일 DB·LLM 지연 조건 비교는 후속 검증으로 제시했다. 참고: [Spring WebFlux 실행 모델](https://docs.spring.io/spring-framework/reference/web/webflux/new-framework.html).
- **Bloom Filter:** 양성 응답은 확정 매칭의 증거가 아니므로 확정 조회·원자적 상태 전이 검증을 후속 보강으로 명시했다. 해당 검증을 이미 구현했다는 주장은 하지 않았다. 참고: [Redis Bloom Filter](https://redis.io/docs/latest/data-types/probabilistic/bloom-filter/).
- **인증·인프라:** JWT 서명과 CI 암호화를 구분했다. state 검증·PKCE·영속 서명키·쓰기 직후 읽기 일관성·호스트 장애 분리는 후속 과제다. DB 복제와 단일 노드 CDC를 다중 노드 HA로 표현하지 않았다.
- **새 수치:** Delishare 평균 응답시간 단축 95.4%, 카드 스레드 수 차이 73.4%, VQA 절대 점수차 0.25975처럼 제공된 값에서 산술적으로 계산한 결과만 사용했다. 나머지 설계 보강은 완료 실적과 구분했다.
